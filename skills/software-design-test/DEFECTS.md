# 观察记录、缺陷分类与报告 / Observation Log, Defect Taxonomy and Reporting

---

## 一、观察记录 / The observation log

模拟用户的产出不是"印象"，是**带时间戳的观察条目**。每条四要素：

| 要素 Element | 要求 Requirement |
| --- | --- |
| 发生了什么 What happened | 用户在画面上做了什么、屏幕上出现了什么（引号原样抄界面文字） |
| 当时的意图 Intent | 这条任务此时想达成什么（意图，不是步骤） |
| 预期 vs 实际 Expected vs observed | 分开写，不许混成一句 |
| 证据 Evidence | 截图相对路径 + 录屏 `mm:ss` |

**观察记录字段 / Observation-log fields**（一行 = 一个可观察事件，**不含解释**）：

```text
会话 ID · 日期 · 人物 · 任务 ID · 时间戳（mm:ss）
观察到的动作（用户做了什么）
原话引用（verbatim，操作者当时的说法）
他声称的期望（"我以为这会保存"）
结果：成功 / 失败 / 需要协助
错误类型：走错路 / 误触 / 找不到 / 状态不符
牵涉的启发式或认知走查问题（第几问失败）
证据链接（截图 + 录屏 mm:ss）
观察者 · 严重级候选
```

**纪律 / Discipline**

- 观察与解释分开写：`观察：按钮无按下态` / `解释：可能是热区没绑事件`。
- 只写"画面可见 / 画面不可见"，不写"应该是""大概"。
- 立刻写，别攒到最后回忆；每个任务卡结束就落盘一条。
- 看不清就写"证据不足"，标 `未验证`。

```json
{

  "at": "2026-10-04T01:10:00.000Z",
  "level": "L1",
  "persona": "P-01 新手 Novice",

  "task_outcome": "partial",

  "element": "E-07 工具栏「导出」",
```

## 二、四类结论 / Four verdicts

| 类别 Kind | 判据 Test | 后续 Next |
| --- | --- | --- |
| 缺陷 Defect | 有画面证据、可复现、期望与实际不符 | 定 S1–S4，进修复顺序 |
| 观察 Observation | 现象为真，但不确定是否违背设计意图 | 交裁决者（用户）判断 |
| 疑点 Suspicion | 疑似问题但未复现 | 标"待复现"，写怀疑依据 |
| 未验证 Unverified | 权限/设备/证据不足 | 写原因与所需条件，**不许写成通过** |

### 2.1 失败的四分类 / Four-way failure classification

任何一次"没成功"，先归类再写报告——**只有 (c) 才是缺陷**：

| 类别 | 含义 | 处理 |
| --- | --- | --- |
| (a) 测试者错误 Tester error | 操作者点错了、理解错了任务卡 | 修正操作重跑；**不计入缺陷**，但若"误解本身很容易发生"则记入可发现性 |
| (b) 观察错误 Observation error | 截图模糊/证据不足，判读不出来 | 重拍；仍然判不了就记"未验证" |
| (c) 产品缺陷 Genuine defect | 真实操作 + 画面证据 + 期望不符 | 进缺陷表 |
| (d) 环境/权限故障 Environment or permission fault | 断网、权限被拒、设备不在 | 记为覆盖缺口或"未验证"，并说明需要什么条件 |

> 依据：GUI 智能体（如 UI-TARS）把"纠错轨迹"与"事后反思"分开训练——**同一个区分用在这里，
> 可以避免把测试事故写成产品缺陷**。

### 2.2 观察前的状态描述 / Describe the state before judging

在判定"这个界面有没有问题"之前，先用文字把画面抄一遍：有哪些元素、哪些可用/禁用、可见文字是什么、
布局如何。**先描述，再判断**——跳过描述直接下结论，是最常见的判断偏差来源。

> Before judging, transcribe the screen into text: elements, enabled/disabled, visible text, layout.
> Describe first, then judge.

## 三、缺陷分类法 / Defect taxonomy

照着这张表走一遍，比盯着空白页想"还有什么问题"有效得多。

| 类别 Category | 画面上长什么样 On screen | 典型发现 Typical |
| --- | --- | --- |
| 功能 Function | 点了没反应、结果与预期不符 | 按钮失效、命令报错、结果算错 |
| 状态 State | 选中态/禁用态/焦点态不对，返回后状态丢失 | 开关回弹、返回后回到首页、草稿丢失 |
| 反馈 Feedback | 没有加载/成功/失败提示，或提示看不懂 | 长时间空白、错误码直接抛给用户 |
| 可发现性 Discoverability | 入口藏太深、术语陌生、必须悬停才知道 | 只有快捷键能到、图标无文字 |
| 导航与焦点 Navigation & focus | Tab 走不到、顺序乱、焦点环丢失 | 焦点陷阱、焦点跑到弹窗背后 |
| 可访问性 Accessibility | 朗读内容缺失、对比度不足、动态字体破版 | 图标按钮无标签、放大后文字被裁 |
| 布局与渲染 Layout | 重叠、裁切、错位、破图、缺字 | 长文本溢出、弹窗被任务栏挡 |
| 内容 Content | 文案歧义、错别字、术语不一致 | "保存"和"应用"含义不同 |
| 性能 Performance | 卡顿、无响应、动画掉帧 | 大列表滚动掉帧、切页白屏 2 秒 |
| 数据完整 Data integrity | 输入被吞、重复写入、列表不刷新 | 中文输入丢字、重复提交 |
| 错误处理 Error handling | 出错无恢复路径、提示指向错误位置 | 断网后卡死、权限被拒无引导 |
| 跨设备 Cross-device | 同一功能在不同端表现不一致 | iPad 横屏布局错、Windows 上快捷键不同 |

## 四、严重级与优先级 / Severity and priority

**严重级 Severity（看伤害）**：

| 级别 | 定义 | 例子 |
| --- | --- | --- |
| **S1 阻断** | 崩溃、数据丢失、主流程完全不可用、隐私泄露 | 导出导致工程损坏；未保存即丢数据 |
| **S2 严重** | 主流程受阻，但有绕行；或关键功能只在部分人物下可用 | 新手只有快捷键能导出 |
| **S3 次要** | 次要功能缺陷、明显视觉问题、需要绕路 | 深色模式下图标看不清 |
| **S4 打磨** | 不影响完成的体验问题 | 间距不齐、文案不统一 |
| **U 无法判定** | 证据不足 | 截图模糊 |

**优先级 Priority（看修的顺序）** 不等于严重级：S3 但阻塞所有新手 → 高优先；S2 但只影响 0.1% 的
冷门路径 → 低优先。报告里两者都要写，别用一个词糊过去。

**谁定 / Who decides**：**严重级由测试方定**（产品影响：崩溃、数据、可达性、绕行方案）；
**优先级由产品/管理层定**（业务紧迫性）。分歧要升级讨论，不许一方覆盖另一方。
四象限处理顺序：高严重高优先 → 低严重高优先（例如品牌文案类）→ 高严重低优先。
把两个字段合成一个，会让分诊变成政治，还会掩盖"这个问题有绕行方案"这一关键信息。

## 五、复现与最小化 / Reproduce and minimize

1. **复现率**：`x/y`，写清 y 是几次尝试。不复现的写"疑点（待复现）"。
2. **最短可靠路径**：一步步删掉不必要的动作，直到再删就不复现。**必须仍然由人手操作完成**，
   不许用脚本"最小化"。
3. **隔离变量**：窗口大小、缩放、深浅色、语言、账号、网络状态、外接屏——一次只改一个。
4. **重拍证据**：最小化之后重新截图，报告里用最小路径的那张。
5. **记录"没复现"**：同一个动作在第 4 次才失败，也要写下来（时序/竞态类缺陷往往如此）。

## 六、缺陷条目的解剖 / Anatomy of a good defect entry

```text
标题 / Title：[人物/级别] 症状 + 位置
  差：导出有问题
  好：[P-01 新手 / L1] 工具栏找不到导出，只有 ⌘E 可用
环境 / Environment：macOS 14.5 · 1920×1080 · 100% · 浅色 · 鼠标（无外接键盘）
前置 / Preconditions：示例工程 sample-01 已打开，无未保存修改
步骤 / Steps：1. … 2. …（只用真实鼠标键盘动作）
预期 / Expected（画面上可见）：…
实际 / Actual（画面上可见）：…
跨模式 / Cross-mode：L1 失败 / L2 失败 / L3 成功
复现率 / Repro rate：3/3
证据 / Evidence：evidence/….png；录屏 00:42–00:58
影响 / Impact：新用户在 L1 无法完成导出，属于"缺鼠标可达路径"
建议 / Suggestion：把「导出」放进「分享」菜单第一层
```

**完整条目字段 / Full issue-record fields**：ID · 标题 · 描述 · 人物 × 任务 · 证据时间点 ·
**频率**（多少个操作者/多少次尝试能复现，写成 `x/y`）· **持续性**（每次都能？还是偶发？）· 影响 ·
根因或违反的启发式 · 严重级（0–4 或 S1–S4；多人评分取均值）· 建议 · 负责人与状态 · 复现步骤。

**"那又怎样"测试 / The "so what?" test**：每条缺陷都要能回答"哪个用户在什么情况下会受损"。
回答不出来的，降级成"观察"，别硬说成缺陷。

**追踪闭环 / Traceability**：每条缺陷都要能顺着
`观察记录 → 证据文件 → 任务卡/人物 → 测试目标` 一路追回去；追不回去的条目说明记录漏了字段。

## 七、报告与去重 / Synthesis and de-duplication

- **按根因合并**：同一根因造成的 5 个症状写成 1 条主缺陷 + 5 个复现点，别把数量刷上去。
- **按人物×场景给覆盖**：报告要能回答"P-01 在新手路径上遇到几条 S2 以上问题"。
- **给出修复顺序**：S1 先行；同根因合并；高影响面的先修。
- **复测纪律**：修复后用**同一任务卡、同一人物、同一级别**复测，结论追加到原条目。

## 八、模拟人物的效度边界 / Validity limits of simulated personas

本工作流里的"人物"是**你自己扮演的观察视角**，不是用户研究结论。三条硬边界：

1. **不许把你的模拟结论写成真实用户结论**。报告里永远写"在 P-01 这个模拟视角下"，
   而不是"新手用户都找不到导出"。
2. **对抗"人物太配合"**：
   - 明确要求每个人物"必须找茬"，而不是"确认能用"；
   - 每个场景至少逼出一次"如果这里失败，用户会怎么做"的回答；
   - 允许并鼓励把结论写成失败；把"一切正常"当成需要额外证据的强主张。
3. **不许用模拟替代真实测试**：高风险功能（支付、医疗、安全）必须补真人会话，
   模拟只用于**扩大覆盖面、提前发现明显问题**。

> 一句话：模拟用户提高的是**发现率**，不是**结论的权威性**。
> Simulated personas raise the **detection rate**, not the **authority** of a conclusion.
